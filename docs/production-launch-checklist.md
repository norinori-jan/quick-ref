# norinori-apps 本番運用開始前最終チェック

## 1. 本番運用開始前の最終チェック項目

### UI
- [ ] quick-ref で受信カードが表示される
- [ ] 既存の検索・フィルタ・タグ表示に影響がない
- [ ] 重複描画や二重初期化が起きない
- [ ] 旧形式の transfer でもカード化できる
- [ ] 受信後に新着として見分けやすい

### Worker
- [ ] `NORINORI_KV` が設定されている
- [ ] 認証トークンが設定されている
- [ ] `PUT /sync/:appName` が成功する
- [ ] `GET /sync/:appName` が成功する
- [ ] 不正リクエストで 400 / 404 / 405 が返る
- [ ] CORS と Authorization の設定が意図どおり動作する

### 各アプリ
- [ ] endpoint が正しく設定されている
- [ ] token が正しく設定されている
- [ ] 送信成功時に quick-ref に反映される
- [ ] 送信失敗時にユーザーに分かる表示がある
- [ ] 送信前後で UI が壊れていない

### 設定値
- [ ] `window.NORINORI_SYNC_ENDPOINT` の値が運用環境に合わせて固定されている
- [ ] `window.NORINORI_SYNC_TOKEN` の値が運用用に置き換わっている
- [ ] 既存のローカル設定と衝突していない

---

## 2. 追加すべき最終微調整（必要なら）

### 小さなコード修正・安全措置
- 受信先コンテナが存在しない場合は、ログだけ出して無視する
- 送信失敗時に localStorage へ fallback する
- 送信/受信で `console.warn` / `console.error` を最小限に残す
- 既存 UI と同名のグローバル変数が衝突しないか確認する
- 旧形式と新形式が混在した場合の優先順を明文化する

### 追加するとよい運用上の配慮
- 受信結果に `timestamp` を表示する
- 新着カードに区別用の badge を付ける
- 履歴が多い場合は件数制限を設ける

---

## 3. 運用開始後の初期 1 週間で確認すべきポイント

- [ ] 送信成功率
- [ ] quick-ref への反映遅延
- [ ] 失敗時の再送しやすさ
- [ ] 旧フォームとの互換性
- [ ] 既存 UI の挙動変化
- [ ] 受信件数が増えた時の表示品質

---

## 4. 運用開始後に発生しやすい問題とその予防策

### 問題: 送信されない
- 予防策: endpoint / token / 認証ヘッダーを事前確認する

### 問題: quick-ref に反映されない
- 予防策: 受信先コンテナの存在と描画ロジックを確認する

### 問題: 旧形式と新形式で表示がぶれる
- 予防策: 優先ルールを固定し、互換処理を明文化する

### 問題: 既存 UI と衝突する
- 予防策: 初期化ガードとイベント分離を維持する

### 問題: 履歴が増えすぎる
- 予防策: 履歴管理方針と保持数の上限を決める

---

## 5. 本番運用フェーズ開始の最終総括

実装基盤は成立しており、現時点では「運用前の最終確認」と「小さな安全措置」の段階です。大きな機能的な欠陥は確認されていませんが、本番開始前に設定値・認証・表示先・互換ルールを固定しておくことが重要です。これらが揃えば、norinori-apps の本番運用を開始する準備は十分に整います。
